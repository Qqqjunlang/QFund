# 持续改进与兼容约定

项目应为后续改进保留空间，保留可编辑源码和维护入口。当前采用本地浏览器工作台、暂缓类别扩展，不等于未来不能调整范围；按实际需求小步演进。

## 已有入口与尚需改进之处

| 变化方向 | 当前可复用的边界 | 后续处理要求 |
|---|---|---|
| 自动时间、参加基金 | ScheduleSettings、WatchlistService独立持久化；调度读取设置 | 沿用统一入口，保留原生效时间与去重/预算，不把当前21:30或513650写入执行规则 |
| 年度交易日历 | calendar模块与JSON资源分开，规则可接收calendar参数 | 当前默认加载文件名仍固定为calendar-2026.json；正式支持多年度资源时集中改加载/资源发现及验证，不在网页/CLI各写判断，也不凭空添加未核验日期 |
| 采集新类别或源站变化 | collectors→parsers→统一update_one→storage/exports链路 | 先验证真实页面和字段，再在采集/解析边界接入；复用保存、导出与错误处理，现有QDII实现并非已支持任意类别的插件平台 |
| 分析与网页交互 | services/analysis及analysis模块承载计算；网页使用服务结果 | 新指标集中定义公式与缺失口径，不让网页、CLI和导出各自维护不同算法 |
| 数据路径、迁移与交付形式 | AppConfig集中推导路径，可显式传入根目录；源码版保留原路径，EXE原型使用用户LOCALAPPDATA/QFund | 不自动发现或迁移旧数据；任意wheel安装和迁移仍需方案，并处理原Windows任务归属，不散落固定盘符 |
| 数据格式升级 | 现有行情库有schema_migrations，配置/资源有schema字段 | 不假称三个库已有统一迁移框架；实际变更时为对应库/配置设计版本与迁移，先备份，在副本验证升级及失败处理，保留原数据和调度账本 |

当前模块分离为后续修改提供了入口，仍有明确限制；不会把“模块化”说成任意新功能无需改代码。固定的安全约束与可变的业务设置也要区分：例如六位代码校验、真实数据口径和任务所有权检查不能为方便扩展而绕过。

## 后续每次变更的约定

1. 先明确需求和影响的模块；可变参数优先用现有设置/资源，新的配置项按需要增加，不预先堆无需求的开关。
2. 网页、CLI和自动更新调用同一业务入口；新增类别、指标或存储方式在相应边界演进，避免复制整套逻辑。
3. 升级保留用户配置、已存行情/修订/导出及名单/调度记录；需要迁移时提供明确方案，不要求用户删库或清空历史才能使用新版本。
4. 保留可编辑源码、锁定依赖、资源和必要文档；交付清单区分程序、用户数据、私有会话和运行环境，后续更换程序不覆盖用户数据/凭据。
5. 验证与变更相称的兼容性：旧数据能读、原设置仍生效、已成功交易日不因升级重采。更新当前约定与验收，记录限制和实际覆盖范围。
6. 只有出现实际需求才抽象或重构；不因“预留空间”擅自引入复杂插件框架、重建环境、迁移数据、扩展功能或改变用户已认可界面。

安装与路径限制见[安装说明](installation.md)，模块和测试入口见[开发说明](development.md)。首次公开发布仍在准备中，不把历史构建或本机验收视为新环境安装已通过。
